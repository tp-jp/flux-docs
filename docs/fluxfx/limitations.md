# 制約と性能

このページはFluxFX 0.0.3のローカル実装に基づく制約をまとめています。技術的に指定できる上限と、快適に動作する容量は異なります。実際の負荷は粒子数、Mesh、モジュール、Trails、画面上の重なり、実行環境によって変わります。

<span id="particle-capacity"></span>

## 粒子の容量

Particle Countは実行前に確保するスロット数です。生存粒子数に合わせて容量を自動伸縮する仕組みではありません。発生要求は空きスロットへ割り当てられ、空きが足りなければ超過分は省略されます。

| 制約 | 実装上の扱い |
| --- | --- |
| 数値精度 | 粒子インデックスを正確に扱うため、最大16,777,216スロット |
| 状態Texture | 1辺は`ceil(sqrt(Particle Count))`。GPUの最大Texture寸法に収まる必要がある |
| 描画Mesh | 容量×1粒子の頂点数・インデックス数が配列とGPU Bufferの上限に収まる必要がある |
| 32bitインデックス | 非対応の場合は全頂点数を65,535以内に制限する |
| メモリ | 数値上の検証を通っても、必要メモリを確保できるとは限らない |

16,777,216は推奨値ではありません。実際の上限はこれらの制約の組み合わせで下がります。生成時にはGPU情報を使った検証も行いますが、制作環境で成功したことが別のGPUでの確保成功を保証するわけではありません。

標準の公開APIには、実行中にParticle Countを増減して描画Meshや状態Bufferをまとめて作り直す操作はありません。用途に合う容量をInspectorで用意します。

<span id="cost-that-remains-with-fewer-living-particles"></span>

## 生存数を減らしても残る負荷

状態はFluxのRenderTextureに保持され、シェーダーの更新パスが確保済みの領域に対して実行されます。描画用Meshも生存数ではなくParticle Countを基準に作成されます。Rateを下げて生存数が減っても、確保したTextureやMeshは小さくなりません。

Stopは新規発生を止めますが、既存粒子の更新は続きます。全粒子が消えたことを理由に、シミュレーション更新全体を自動停止する処理もありません。Pauseはシミュレーション更新を止めますが、残っている粒子の描画や確保済みメモリをなくす操作ではありません。

Culling Boundsは描画範囲の判定に使われます。カメラ外になったからといって、FluxParticleSystemのUpdateまで自動的に停止する仕組みではありません。

<span id="buffers-and-memory-estimates"></span>

## Bufferとメモリの目安

FluxBufferはARGBFloat形式で、1テクセルは4成分×32bit、データ部分は16バイトです。1辺を`W`とすると、1枚あたりのデータ量の目安は`W × W × 16`バイトになります。

状態ページは読み書きを切り替えるために2枚ずつ持ちます。それ以外にも発生入力、空きスロットの集計、Lookup用Texture、Trailsなどが必要です。状態ページ数は構成によって変わるため、「粒子数×固定のバイト数」だけで全体の使用量は求められません。

例えば65,536スロットなら状態Textureの1辺は256で、1枚のデータ部分は約1 MiB、1ページの2枚で約2 MiBです。これは状態Textureだけの概算であり、Mesh、補助Buffer、ドライバー側の管理領域などは含みません。

<span id="billboard-and-mesh-rendering"></span>

## BillboardとMeshの描画

Billboardは1粒子あたり4頂点・6インデックスです。Meshモードは、指定したMeshの頂点とインデックスを容量分複製して描画用Meshを作ります。複雑なMeshを使うほど、初期化時の配列生成、メモリ使用量、描画時の頂点処理が増えます。

Meshは読み取り可能で、頂点・三角形があり、すべてのサブメッシュがTrianglesである必要があります。元MeshのMaterial構成を粒子ごとに再現する仕組みではなく、FluxFXの生成した描画Materialを使用します。

Alpha・Additiveは深度書き込みを行いません。大きい粒子や広い軌跡が重なると、同じ画面領域を繰り返し描画する負荷が増えます。また、現在の描画Meshは粒子単位の奥行きソートを行わないため、Alphaで重なり順が期待どおりにならないことがあります。

Billboardの回転はZ軸のみです。MeshではXYZ回転を使えます。描画範囲はRendererのローカル座標のCulling Boundsで指定し、World空間の粒子やTrailsが残る位置も含めます。

<span id="modules-and-runtime-changes"></span>

## モジュールと実行時変更

モジュールは生成時に組み込まれます。同じ種類を複数追加することはできず、処理順は定義の依存関係で決まります。実行時に未追加のモジュールを新規追加するAPIではありません。

無効化しても、そのモジュールの構成とパラメーターは残ります。無効状態なら削除時と同じメモリ・生成構成になるとは限りません。使わないモジュールはInspectorで削除して、構成を再生成します。

StaticのStart Lifetime・Start Color・Start Size・Start Rotation・Texture Sheet AnimationのTilesは、初回シミュレーション更新後にロックされます。ClearやRestartでは解除されません。変更できる値と反映時期は[実行時のパラメーター変更](./runtime-parameters.md)を参照してください。

Curveは寿命の0〜1区間を128点でサンプリングします。GradientのBlendも128点、Fixedはキーの区間に応じた値を使います。これらは生成したLookupデータを評価するため、非常に細かいCurveの変化は実際の表示で確認します。実行中にCurveやGradientそのものを編集する公開操作はありません。

<span id="trail-cost-and-constraints"></span>

## Trailsの負荷と制約

記録対象数は`min(Particle Count, Max Trails)`です。Points Per Trailを`P`とすると、履歴・管理用Bufferは`P + 2`枚、描画区間は`P − 1`個になります。実行用構成では区間ごとにMaterialとMeshRendererを持つため、点数を増やすと履歴メモリだけでなく描画処理も増えます。

| 項目 | 制約 |
| --- | --- |
| Points Per Trail | 2以上 |
| Duration | 正の有限値。点数から求める記録間隔も有効である必要がある |
| 記録頻度 | 1回のシミュレーション更新で最大1点。更新間の移動を補間して複数記録しない |
| 記録対象 | 容量内の分散したスロットを対象にする。生存粒子だけを動的に選び直すわけではない |
| 粒子の消滅 | 軌跡も消える。消滅後にDuration秒残す動作ではない |
| 座標 | Local空間でも履歴はワールド座標で記録する |
| 見た目 | 専用の色・幅・アルファブレンドを使う。粒子の色・点滅・テクスチャ設定を引き継がない |

最初はMax TrailsとPoints Per Trailを小さくし、必要な滑らかさに合わせて増やします。詳しくは[Trails](./trails.md)を参照してください。

<span id="readback-environments-and-synchronization"></span>

## 読み戻し・実行環境・同期

生存数の取得にはGPU側での集計と非同期読み戻しが必要です。要求は0.2秒以上の間隔で、処理中は次の要求を開始できません。結果は遅れて届くため、毎フレームの正確な生存数としては扱えません。表示用途なら必要な頻度で要求します。

FluxFXはFluxのARGBFloat RenderTextureとシェーダー処理を利用し、生存数の取得にはVRCAsyncGPUReadbackを利用します。CPUシミュレーションへ自動的に切り替える実装はありません。必要なGPU機能、Shaderのコンパイル、描画、読み戻しは対象環境で確認してください。この実装確認だけで、各プラットフォームへの対応を保証するものではありません。

シミュレーションは各クライアントで動作し、再生操作・パラメーター・粒子状態を自動同期しません。呼び出し側で同じ再生操作を共有しても、更新間隔やGPU演算まで同一になるとは限りません。粒子位置が全クライアントで完全一致することを前提にしない設計にします。

<span id="compare-performance"></span>

## 負荷を比較する手順

1. 対象環境で、同じカメラ位置・解像度・再生時間に揃えて比較します。
2. まずParticle Countを下げ、容量に伴う更新・描画負荷の影響を確認します。
3. Meshを簡単な形状やBillboardに変え、頂点数の影響を確認します。
4. 粒子サイズや重なりを減らし、画面を覆う描画負荷を確認します。
5. TrailsのMax TrailsとPoints Per Trailを下げて比較します。
6. 不要なモジュールを削除した構成と比較し、生存数の取得頻度も見直します。

設定は一度に1つずつ変えます。発生頻度を下げただけの場合と容量を下げた場合、StopとPauseなど、異なる操作を混同しないようにします。初期化時の負荷と、再生中に継続する負荷も分けて確認してください。

特定の粒子数でのフレームレートは実装だけでは決まりません。プレビューで調整した後、実際のワールドで他の描画や処理と合わせて評価します。表示や生成が失敗する場合は[トラブルシューティング](./troubleshooting.md)を参照してください。
