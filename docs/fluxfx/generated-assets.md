# 生成物の管理 {#generated-assets}

FluxFXは、生成したShader・固定HLSL・Materialなどの所有情報と依存関係を記録し、未使用になった生成物を整理します。使用中の生成物と、その依存ファイルは保持します。

通常は起動時の自動整理を利用できます。削除候補や保持理由を確認したい場合や、独自の生成先を使っている場合は、手動で分析してから整理してください。

## 生成先と管理対象 {#scope}

既定の生成先は`Assets/FluxFX/Generated`です。生成処理が登録したファイルだけが整理対象になります。

| 生成先ルートからの相対パス | 内容 |
| --- | --- |
| `Cache/Shaders` | 生成Shaderと、生成時の内容を保存した固定HLSL |
| `Cache/Lookups` | Curve・Gradientなどの参照用Texture |
| `Cache/Meshes` | 共有する生成Mesh |
| `Sessions/<セッションID>/Materials` | 生成セッションごとのMaterial |

自動整理は既定の生成先だけを対象にします。独自の生成先は、手動整理の「生成先ルート」に指定してください。単にフォルダー内に置いたファイルや、カスタムモジュール作者が用意した元のC#・HLSLは、生成物として登録されていなければ整理対象になりません。

## 手動で分析・整理する {#manual-cleanup}

1. Play・ビルド・生成処理が終わってから、**Tools → FluxFX → Clean Unused Generated Assets** を開きます。画面を開くだけでは走査しません。
2. **生成先ルート / Generation Root** を確認します。独自の生成先の場合は、生成セッションで登録した`Assets`配下のルートを指定します。
3. **生成物を分析 / Analyze Generated Assets** を押します。この操作ではAssetを削除しません。
4. 削除候補の件数・容量と、各ファイルの保持理由・参照元を確認します。候補の容量には`.meta`も含まれます。
5. **確認した未使用生成物を削除 / Delete Reviewed Unused Assets** を押します。
6. 削除・保持・失敗の結果を確認します。診断結果のJSONパスも画面に表示されます。

削除時には参照とGUIDを再確認します。分析後に新しく候補になったファイルは削除せず、確認済みの候補だけを対象にします。生成先ルートを変更した場合は、分析し直してください。

表示言語はFluxFX Inspectorの[言語設定](./inspector-preview.md#use-the-settings-panel)に従います。コンパイル・Import・Play・ビルドなどの処理中は、分析・削除ボタンが無効になります。

**手動整理には、自動整理の24時間の実行間隔と保持期間を適用しません。** 最近使ったCacheや失敗した生成物も、未使用なら候補になります。[参照と所有情報による保護](#protection)は手動でも行います。

## 起動時の自動整理 {#automatic-cleanup}

自動整理は**未設定ならON**です。すでに保存されたOFF設定は維持します。整理画面の **自動整理 / Automatic Cleanup**、または **Tools → FluxFX → Automatic Generated Asset Cleanup** で切り替えます。

初期Import・コンパイルと生成セッションの復旧が完了した後、最初に実行可能になったタイミングで、起動ごとに一度だけ判定します。自動整理がONで、次の両方を満たす場合に実行します。

- 整理の予約がある、または生成物の保持期限を迎えている。
- 前回の自動全体走査の開始から24時間以上経過している。走査時刻の記録がなければ、この制限を受けない。

旧形式のスケジュールを移行する場合は、記録されている走査時刻を引き継ぎます。手動の分析・整理では、自動整理の24時間の起点を更新しません。

条件を満たさなかった場合も、その起動での判定は終了します。再コンパイル・ドメインリロード・ON/OFFの切り替えでは再判定しません。すでにFluxFXを使用しているEditorへ更新を導入しても、新しい起動としては扱いません。Editorを開いたまま24時間が経過しても、途中で自動実行しません。

判定より先にPlay・ビルド・生成・Preview操作が始まった場合は、その起動での自動整理を見送ります。未完了の予約は次回起動へ持ち越します。バッチモードでは起動時の自動整理を行いません。

自動整理は進捗表示とキャンセルに対応します。全体走査が始まった後にキャンセル・失敗した場合も、24時間の実行間隔を維持し、未完了の予約を残します。走査開始前にキャンセルした場合は24時間の起点を更新しませんが、その起動では再実行しません。すでに削除したファイルはキャンセルで復元されません。

自動整理では、説明用の詳細な参照元の特定を省きますが、参照されているファイルを保護する判定は行います。参照確認や削除はEditor上で実行されるため、処理中に待ち時間が発生する場合があります。

### 自動整理の保持期間 {#retention}

| 対象 | 保持期間 |
| --- | --- |
| 共有Cache | 最終利用から24時間 |
| 失敗・中断した生成物 | セッション終了から24時間 |

両方に該当する場合は、どちらの保持期間も過ぎるまで保持します。**期限切れは削除の確定ではなく、参照を再確認する条件です。** 参照が残っていれば削除しません。

## 削除されないもの {#protection}

| 条件 | 保護の内容 |
| --- | --- |
| 実行中の生成セッションがある | 対象ルートの整理を見送る。経過時間だけではセッションを終了扱いにしない |
| 保存Assetから参照されている | 保存Scene・Prefabなどが使う生成物を保持する |
| 未保存Scene・Prefab Stage・使用中オブジェクトから参照されている | 保存前の参照も保護する |
| 保持する生成物に依存ファイルがある | 固定HLSLなどへの依存もたどって保持する |
| 所有記録がない、GUID・種別・配置が一致しない | 管理対象として削除しない |
| 固定Shader／HLSLの内容が記録と異なる | 変更されたファイルを保持する |
| 依存関係に循環がある | 循環に含まれる生成物とその依存先を保持する |

削除は参照元から依存先の順に行います。例えばMaterial → Shader → 固定HLSLという依存なら、この順で削除します。参照元の削除に失敗した場合は、その依存先を保持します。管理記録を読み取れない場合も削除を進めず、診断結果を返します。

## 管理記録と結果の保存先 {#records}

| パス | 内容 |
| --- | --- |
| `ProjectSettings/FluxFXGeneration/Roots` | 生成先ごとの所有台帳。管理対象の識別情報と依存関係 |
| `ProjectSettings/FluxFXGeneration/CleanupSchedule.json` | 整理の予約、走査時刻、次の保持期限の確認時刻 |
| `Library/FluxFX/GenerationSessions` | 生成セッションの実行履歴 |
| `Temp/FluxFX/GenerationCleanup` | 分析・整理結果のJSON |

所有情報はLibraryの実行履歴から分離しているため、Libraryを再作成しても台帳は残ります。分析時には、旧管理記録を台帳へ移行することがあります。Tempの結果は永続的な履歴ではないため、調査に必要なものは別途保存してください。

## 拡張開発者向けAPI {#api}

Editorコードでは、`TpLab.Flux.FX.Editor.Build`名前空間の`FluxParticleGenerationCleanup`を使います。Runtime・UdonSharp向けのAPIではありません。

| API | 用途 |
| --- | --- |
| `Analyze(root)` | Assetを削除せず、候補・保持理由・参照元を含む`FluxParticleGenerationCleanupReport`を取得する |
| `CollectReviewed(report)` | `Analyze`の結果を利用者が確認した後に呼ぶ。参照とGUIDを再確認し、その結果の候補だけを整理する |
| `CollectWithReport(root)` | 最新の状態を分析して整理し、詳細な結果を取得する。事前に確認した候補だけに限定するAPIではない |
| `Collect(root)` | 整理して削除したAsset数を返す。管理記録などの処理に失敗した場合は例外を通知する |
| `Request()` | 次回起動時の再確認を予約する。このEditor実行中には自動走査しない |
| `AutomaticCleanupEnabled` | 自動整理の有効状態を取得・保存する。変更だけでは再判定しない |

`root`の省略時は`FluxParticleGenerationSession.DefaultRoot`を使います。独自ルートは生成セッションの`Begin`で登録したものを指定してください。`Request()`による自動整理の対象は既定ルートです。

`Analyze`はAssetを削除しませんが、必要に応じて旧記録を移行し、全体走査を開始した場合はその時刻を記録します。診断JSONも保存します。`CollectWithReport`と`Collect`は利用者の確認画面を開かずに削除を実行します。確認画面を実装する場合は、`Analyze`で結果を表示し、確認後に`CollectReviewed`へ渡します。

`Analyze`・各`Collect`には、自動整理の24時間制限を適用しません。実行中セッションや参照、所有情報の保護は共通です。生成・HLSL固定・セッション終了の責任は生成側にあり、整理APIはこれらを代行しません。

### 結果の確認 {#report}

`FluxParticleGenerationCleanupReport`の`CandidateCount`・`CandidateBytes`・`DeletedCount`で件数と容量を取得できます。`items`にはパス、GUID、種別、状態、理由、参照元が入ります。状態は`Candidate`・`Keep`・`Missing`・`Deleted`・`Failed`です。

`blocked`は処理が見送られた・中断された状態、`cancelled`はキャンセル、`failed`は分析や管理記録処理の失敗です。**個別の削除失敗は`failed`だけでは判定できません。** `items`の`status == "Failed"`も確認し、`diagnostics`と`logPath`を調べてください。`fullScan`で全体の参照走査を開始したか確認できます。

`Collect`の戻り値が0でも、候補がない場合と、処理が見送られた場合や個別の削除が失敗した場合を区別できません。結果を判定する必要がある拡張では`CollectWithReport`を使ってください。

生成処理との関係は[全体構成](./architecture.md)、生成結果の調査は[検証と性能](./validation-and-performance.md)を参照してください。
